# MaterialBook — Security review (T19)

Scope: backend (all modules), nginx (REMOVED 2026-11-09, see section 8), docker-compose, scripts, `.env` handling, dependency licenses and known vulnerabilities. Frontend was reviewed read-only (T17c owns `frontend/**`).
Method: read the code (every controller, every `JdbcTemplate`/JPQL query, auth/session code, config), wrote regression tests for each fix, ran Trivy and the license plugins. Findings are things that were actually found in this repo; "verified OK" items are listed separately so nobody re-checks them.

Severity: HIGH = exploitable with real impact; MEDIUM = real weakness needing a precondition; LOW = hardening / defence in depth; INFO = by design or note.
Status: FIXED (code + test), ACCEPTED (conscious trade-off, rationale given), OPEN (needs a decision or work outside T19's lane).

## 2. Verified OK (read the code / tested; no finding)

**Authorization**
- Default deny: `anyRequest().authenticated()`; stateless; CSRF disabled is correct for bearer tokens, and the two cookie-based endpoints (`/auth/refresh`, `/auth/logout`) require `X-Requested-With: MaterialBook` on top of `SameSite=Strict`.
- All permission codes in `@PreAuthorize` exist in V2/V6 seeds (now test-enforced). Report exports require `REPORT.EXPORT` **and** the module's export permission; the transaction PDF checks `MATERIAL_<type>.EXPORT` against the record's real type (an IN-export user cannot print an OUT challan).
- Single-tenant app: there is no per-user data ownership, so classic IDOR does not exist; "ownership" is the module permission. Attachments inherit the owner's module permission (`MATERIAL_IN|OUT`, `EXPENSE`, `PAYMENT`) for view/upload/delete and are frozen on CANCELLED owners. `GET /attachments/{id}/content` re-checks VIEW on the owner. Audit logs: `AUDIT.VIEW` only; secrets are redacted by key fragment (`password`, `token`, `secret`).
- Privilege escalation: SUPER_ADMIN can only be assigned/removed/modified by a SUPER_ADMIN; granting roles, role permissions or overrides is limited to permissions the actor holds; no self-override, no removing own admin role, last active SUPER_ADMIN protected, the SUPER_ADMIN role is immutable, system-role permissions need SUPER_ADMIN, DENY/ALLOW overrides cannot be applied to a SUPER_ADMIN user by an admin.
- CANCELLED / INACTIVE rules: edit and double-cancel of material (row-locked + version), expenses (version) and payments (conditional UPDATE) are rejected; inactive party/product cannot be used in new/edited documents; opening stock only for products without movements; attachments on cancelled records are read-only.
- Pagination caps exist everywhere (`size` <= 200, or clamped in the service). No client-controlled sort or group-by reaches SQL.

**Injection / output**
- Every `JdbcTemplate`/JPQL/native query binds values (`:name`/`?`). The only concatenated fragments come from enums or constants (`GroupBy`, `OwnerType.fkColumn/table`, `asc|desc` from a boolean, WHERE builders that append fixed text). No SSRF surface (no outbound calls for files). Storage keys are `yyyy/MM/uuid`, never user input, and `LocalFileStorage` additionally rejects `..`, absolute paths and symlinks out of the root (LocalFileStorageTest); the original filename only appears in `Content-Disposition: attachment; filename*=UTF-8''...` (RFC 5987 percent-encoded) of the authenticated content endpoint and report filenames are whitelisted to `[A-Za-z0-9_-]`. PDF text is sanitised (control characters stripped, unsupported glyphs replaced) before `showText`.

**Auth / session**
- BCrypt(12); unknown-user login still performs one BCrypt compare; one generic message for unknown/inactive/locked/wrong password; failed-login counter protected by a row lock (`findByMobileForUpdate`). Refresh token: 256-bit random, SHA-256 stored, rotated, reuse revokes the family, concurrent refresh of the same token is serialised (the loser looks like a reuse and ends that session, acceptable; the frontend uses a single in-flight refresh). Cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` (Secure forced in prod). Logout revokes the family; change-password, reset-password and deactivate revoke all refresh tokens. Access token is held in memory only on the client (frontend grep: no `localStorage`/`sessionStorage`, no `dangerouslySetInnerHTML`, `window.open` uses `noopener,noreferrer`).
- CORS: single exact origin, explicit methods/headers, credentials only for that origin, required (no default) in prod. Test: `CorsAndMassAssignmentTest` (foreign origin, suffix look-alike, other port, other scheme all get no `Access-Control-Allow-Origin`).

**Data / config**
- `server.error.*` never include message/stack/binding errors; `GlobalExceptionHandler` returns generic 500 text; JPA `open-in-view: false`, `ddl-auto: validate`, SQL logging off; actuator exposes `health` only with `show-details: never`, and nginx returns 404 for `/actuator/`. No secrets, tokens or passwords are logged (grep of every `log.*` call; the bootstrap log line prints the admin mobile, not the password). Multipart limits 10/12 MB (nginx 12 MB). Upload validation: Tika magic-byte detection + extension + declared type must agree, 10 MB / 5 MB caps, sanitised name, SSE-S3, 5-minute presigned GET.
- Secret scan: no keys/tokens/passwords in the repo (regex sweep + Trivy secret scanner over backend, frontend, nginx, scripts, docs: 0 findings). `.env`, certs and backups are git-ignored; `.env.example` only has placeholders and the JWT placeholder is now rejected at startup. Test passwords exist only in test sources.

## 8. Single-image change (2026-11-09): nginx removed, the app serves the SPA and the headers
What moved from nginx into the application (all covered by `StaticAppAndHeadersTest`, `ContentSecurityHeadersTest`, `ProdProfileTest`, `AuthorizationCoverageTest`):
* **Response headers** (CSP `default-src 'self'` ..., nosniff, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `Permissions-Policy`, COOP, CORP, HSTS on HTTPS) via Spring Security on every response, including 401/404 problem+json. The stricter `default-src 'none'; sandbox` CSP of attachment/branding/product-image responses is set by the controller and wins (exactly one CSP header; tested).
* **Static serving / SPA fallback**: only `classpath:/static/` is exposed (never the classpath root), no directory listing, no source maps are produced by the build, path-traversal attempts (`..`, `%2e%2e`, `%2f`) are rejected by Spring Security's firewall (400) or 404. The fallback to `index.html` applies only to GET/HEAD of non-`/api`, non-`/actuator`, non-docs paths without a file extension; unknown `/api/**` stays 401/404 problem+json. Security rules: every `/api/**` rule is unchanged and precedes the new `permitAll` for static GET/HEAD; all other methods/paths still need authentication.
* **TLS**: optional built-in (Spring Boot PEM, TLS 1.3/1.2 only, `SERVER_SSL_*`), or operator proxy. HSTS only on HTTPS requests. `server.server-header` blank (no software banner). gzip on text/JSON/SVG.
* **Cookie**: `AUTH_COOKIE_SECURE` defaults to true in prod and may now be set to false by the operator for plain-HTTP use (previously forced). Setting it false on an internet-facing deployment weakens the refresh cookie (it could be sent over HTTP): do not.
* **CORS**: the SPA is same-origin, so `CORS_ALLOWED_ORIGIN` is blank/optional in prod (no cross-origin caller allowed unless configured).

| `/actuator/` blocked at the edge | nginx | `/actuator/health` is reachable by anyone who can reach the port (status only, `show-details: never`); everything else under `/actuator` is not exposed | block `/actuator` at your proxy if even this is unwanted |
| Client-supplied `X-Forwarded-For` overwritten | nginx | **Measured on the throwaway stack:** with Tomcat's `forward-headers-strategy=native` and the port reached directly through Docker (client address is private/bridge), 90 login attempts with a different spoofed `X-Forwarded-For` each were ALL accepted (no 429), while without the header 58 of 90 were 429; the unthrottled flood also exhausted the 10-connection DB pool (2 x 500). | `docker-compose.yml` therefore defaults `SERVER_FORWARD_HEADERS_STRATEGY` to `none` (re-measured: spoofing then yields 27 x 429 of 60). Set `FORWARD_HEADERS_STRATEGY=native` only behind a proxy that OVERWRITES `X-Forwarded-For` (and restrict `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES` to it). Account lockout (5 failures/15 min per user) applies either way. A plain `java -jar` run keeps the `application.yml` default `native` |

Residual notes: Docker Desktop shows every client as the bridge gateway address (one shared rate-limit bucket) - expected only on developer machines. Built-in TLS does not renew certificates and has no OCSP stapling. Linux: the private key bind-mounted into the container must be readable by uid 10001. Not verified on a real Linux host.
